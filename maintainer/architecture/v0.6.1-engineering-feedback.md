# v0.6.1-rev1 Engineering Feedback After Stage I

## Status
- prepared after Stage I exit review
- intended to support v0.6.1 → v0.6 merge planning

## Scope
This note records whether Stage I implementation exposed any places where v0.6.1-rev1 should be revised, clarified, or merged more carefully before the unified v0.6 documentation pass.

## Overall judgment
Stage I did **not** expose any blocking contradiction or correctness defect in v0.6.1-rev1.

The theory proved implementation-ready across the Stage I target surface:
- §1 rate sensing
- §2 memory layering
- §3 inherited priors L3 path

The main engineering feedback is therefore **clarification-oriented**, not a request to rewrite the theory from scratch.

## Recommended clarifications before v0.6 merge

### 1. Clarify the working-memory integration-table wording
- **Current engineering finding**:
  - Stage I implemented `WorkingMemory` as the deliberation-facing read surface assembled after current-cycle sensing and drive update.
- **Why clarification is needed**:
  - The v0.6.1-rev1 §2.5 table can be read too literally, as if working memory should become a separate owner inside L1 or L2.
- **Recommended merge wording**:
  - Keep the table’s intent, but clarify that the L1/L2 cells are satisfied by the existing in-cycle substrate rather than by introducing a second working-memory controller before sensing or drive update.
- **Engineering basis**:
  - `maintainer/architecture/memory-decision-integration-audit.md`

### 2. Clarify the exact Stage-I scope of semantic memory
- **Current engineering finding**:
  - Stage I landed:
    - first-class append-only semantic storage
    - exact query-by-topic / query-by-scope read paths
    - bounded L3 candidate-prior participation
  - Stage I did **not** land:
    - automatic episodic → semantic extraction
    - semantic memory → L2 drive-weight modification
- **Why clarification is needed**:
  - Without this distinction, readers may overread v0.6.1-rev1 as if Stage I committed to a fuller semantic system than was intended.
- **Recommended merge wording**:
  - Preserve the interface-first commitment explicitly:
    - Stage I guarantees semantic storage + retrieval + bounded L3 participation.
    - semantic extraction automation and semantic → L2 drive-weight effects remain later work.
- **Engineering basis**:
  - `docs/eva-framework-implementation.md`
  - `maintainer/architecture/memory-decision-integration-audit.md`

### 3. Clarify that Stage-I procedural memory can legitimately reuse the existing habit path
- **Current engineering finding**:
  - Stage I chose path (b): formalize and slightly extend the existing `habit_bias.jsonl` / habit shaping path rather than introduce a separate `procedural_memory.jsonl`.
- **Why clarification is needed**:
  - The theory allows multiple realizations, but the merged v0.6 text should not accidentally imply that a separate procedural store is mandatory for Stage-I adequacy.
- **Recommended merge wording**:
  - State that Stage-I procedural memory is satisfied if condition-matched action patterns become explicit, bounded, mediator-gated, and runtime-active — even when backed by the existing habit path.
- **Engineering basis**:
  - `docs/eva-framework-implementation.md`
  - `maintainer/architecture/stage-i-i3-procedural-memory-decision.md`

### 4. Keep inherited-prior independence and same-scenario restriction explicit
- **Current engineering finding**:
  - The Stage I implementation worked cleanly because:
    - distillation stayed outside `eva/` and `scenarios/`
    - bundles remained same-scenario only
    - runtime participation stayed advisory at L3
- **Why clarification is needed**:
  - These constraints are not incidental implementation choices; they are part of why inherited priors did not create a second decision lane.
- **Recommended merge wording**:
  - Keep all three points explicit in the merged v0.6 text:
    - external distillation package
    - same-scenario-only bundling
    - advisory-only L3 runtime participation
- **Engineering basis**:
  - `docs/eva-framework-implementation.md`
  - `maintainer/architecture/memory-decision-integration-audit.md`

### 5. If Crafter-oriented appendix language is merged, update it to reflect landed local-view decomposition
- **Current engineering finding**:
  - The Stage I engineering landing decomposed the earlier `local_view_state` simplification into separate threat / resource / utility signals.
- **Why clarification is needed**:
  - If the unified v0.6 text preserves Crafter-oriented appendix or scenario examples, wording that assumes one collapsed `local_view_state` would lag behind the landed implementation.
- **Recommended merge wording**:
  - Reflect the engineering reality:
    - local-view signals remain optional-tier and bounded
    - but can be decomposed into multiple scenario-owned sub-signals without changing framework ownership
- **Engineering basis**:
  - `scenarios/crafter/SPEC.md`
  - `maintainer/development/stage-i-progress.md`

## What Stage I did not reveal as theory problems

### 1. Exploration defer is a scope decision, not a theory defect
Stage I’s defer of v0.6.1-rev1 §4 should not be treated as evidence that §4 needs conceptual rollback.
It was a deliberate scope and sequencing choice.

### 2. White-list boundary friction is a process issue, not a theory issue
Stage I required minor-adaptation changes in `eva/l3_deliberation/` and `eva/kernel/` to consume the new memory-layer and inherited-prior seams.
That is best recorded as maintainer workflow guidance, not as a revision request against the theory itself.

## Final judgment
Stage I implementation supports merging v0.6.1-rev1 into the unified v0.6 document.

Recommended pre-merge stance:
- no blocking theoretical rewrite needed
- perform a clarification pass during merge
- carry forward the already documented implementation follow-ups separately from theory merge work
