## 1. What this work is and is not

This is **Phase A of the v0.6 refactor**. Phase A is **framework/scenario separation under behavior equivalence**. Nothing about agent behavior changes during Phase A; only code organization changes.

What Phase A is:

- Lift Linux-specific content (drive types, sensor implementations, action implementations, anchor reasons, outcome observer logic) out of `eva/` and into `scenarios/linux_runtime/`
- Establish injection interfaces in `eva/` that allow scenarios to be plugged in
- Establish the directory structure: `eva/` (framework), `scenarios/` (top-level peer), `runners/` (per-scenario entry points), `stability_metrics/` (independent top-level)
- Migrate documentation: split `docs/eva-agent-full-implementation.md` into `docs/eva-framework-implementation.md` (framework) and `scenarios/linux_runtime/SPEC.md` (Linux scenario), archive original

What Phase A is **not**:

- Not adding new behavior. No new drive types. No new sensors. No new actions. No new anchor rules. No new outcome dimensions.
- Not adding multi-dimensional outcome implementation. The outcome system currently uses a particular schema; Phase A keeps that schema and only moves its definition to the right location. Multi-dimensional outcome is Phase B.
- Not adding prior skill / habit separation. Phase A keeps the current skill_library structure; the prior/habit/inherited separation is Phase B.
- Not adding persistence target abstraction. Phase A keeps the current implicit Level-1-only persistence; the formal abstraction is Phase B.
- Not adding stability metrics. The `stability_metrics/` directory is created with a placeholder; the actual implementation is Phase B.
- Not adding Crafter scenario. That is Phase C.
- Not changing what Linux EVA does. Linux EVA after Phase A behaves identically to Linux EVA before Phase A.

The reason for this separation is workflow integrity. If Phase A mixes refactor with new functionality, regression failure becomes ambiguous (was it the move or the new feature?). Behavior equivalence under refactor must be verifiable by running the same tests and seeing them all pass.

---

## 2. The behavior equivalence criterion

**Definition**: Phase A is complete when, with the new code organization in place, every existing test in the test suite passes without modification, and the agent's runtime behavior on the same inputs produces the same outputs.

This means specifically:

- All existing unit tests pass without modification to test logic. (Test imports may need updating to reflect new module locations; this is acceptable.)
- All existing integration tests pass without modification.
- Running the Linux EVA agent on a representative scenario produces equivalent traces (deliberation_audit, episodic_memory, learning_outcomes, habit_bias, llm_advisory_audit) compared to a pre-refactor baseline run.
- Persistent state files have equivalent schemas (any schema changes require explicit architect approval, which Phase A is not authorized to request).

If any test requires logic modification (not just import path update) to pass, that is a behavior change. Behavior changes are not authorized in Phase A. If a test cannot pass with only import updates, stop and report; do not modify test logic to make it pass.

## 4. Slice sequence

Phase A is decomposed into 8 slices. The sequence matters: each slice depends on previous slices being complete and tested.

### Slice A-1: Directory structure creation

Create the target directory layout. Empty packages with `__init__.py` files. Add placeholder `README.md` files where they help. No code is moved yet.

**Completion**: Directory structure exists, full regression passes (since no code logic changed).

### Slice A-2: Drive registry separation

Move `eva/l2_drive/drive_registry.py` content out of `eva/`. The framework-level drive registry interface stays in `eva/l2_drive/drive_registry.py` but contains only:
- Abstract `DriveRegistry` and `DrivePreset` interfaces
- Generic `DriveUpdatePolicy` parameter structure (the dataclass; specific values move out)

Concrete content moves to `scenarios/linux_runtime/drive_preset.py`:
- `DRIVE_TYPES = ("survival", "integrity", "continuity", "curiosity")`
- `DRIVE_TYPE_BY_DIMENSION` mapping
- Default `DriveUpdatePolicy` parameter values used by Linux runtime
- Linux-specific severity / threat bonus / curiosity recovery configurations

`eva/l2_drive/` framework code that currently imports the constants must be modified to receive them via injection from the loaded scenario.

The runner `runners/run_linux.py` loads the Linux drive preset and injects it into the framework at startup.

**Completion**: All drive-related tests pass without logic modification (imports may update). Framework code in `eva/l2_drive/` no longer references survival / integrity / continuity / curiosity by name.

### Slice A-3: Sensor implementation separation

Move concrete sensor implementations from `eva/l1_sensing/` to `scenarios/linux_runtime/sensors/`. The sensor registry mechanism (already plugin-style from D-2) stays in `eva/l1_sensing/`.

Specifically:
- Heartbeat sensor → `scenarios/linux_runtime/sensors/heartbeat.py`
- Instance validity sensor → `scenarios/linux_runtime/sensors/instance.py`
- Disk / resource sensors → `scenarios/linux_runtime/sensors/resource.py`
- Process / runtime integrity sensors → `scenarios/linux_runtime/sensors/runtime.py`
- Anomaly accumulation sensor → `scenarios/linux_runtime/sensors/anomaly.py`

The runner registers these sensors with the framework at startup.

**Completion**: All sensor-related tests pass. Framework `eva/l1_sensing/` contains no Linux-specific sensor logic.

### Slice A-4: Action implementation separation

Move concrete actions from `eva/l3_deliberation/tool_edge/` to `scenarios/linux_runtime/actions/`. The tool registry mechanism stays in `eva/l3_deliberation/tool_edge/`.

Specifically:
- `RECHECK_ACTION`, `REPAIR_ACTION`, `ESCALATE_ACTION` constants and their handlers → `scenarios/linux_runtime/actions/`
- Action-to-posture, action-to-state-mode, action-to-allowed-states mappings → `scenarios/linux_runtime/actions/registry.py`
- Linux-specific `select_integrity_response`, bridge_policy logic → Linux scenario

Framework `eva/l3_deliberation/tool_edge/` retains:
- Tool registry interface (registration, lookup)
- ReleaseToken validation logic
- Action execution path (token in → handler call → outcome out)
- `ActionSpec` data structure (declares side-effect class, anchor applicability)

**Completion**: All tool-edge and action-related tests pass. Framework code does not reference recheck / repair / escalate by name.

### Slice A-5: Anchor rules and reasons separation

Move Linux-specific anchor content from `eva/anchor/` to `scenarios/linux_runtime/anchors/`:
- Linux anchor reasons (`runtime_files_missing`, `recent_yield_detected`, etc.)
- Linux-specific admission gate definitions
- Linux candidate profile rules (`STABILIZE_FIRST_PROFILE`, `ESCALATE_FIRST_PROFILE` and their conditions)
- High-risk integrity reason set

Framework `eva/anchor/` retains:
- Anchor system mechanism (pre-generative restriction logic)
- ActionDomain construction framework
- Admission gate framework (the structure; specific gate rules are scenario-supplied)
- Candidate profile interface (the type system; specific profiles are scenario-supplied)

This is the most delicate slice. Anchor logic is core to EVA's safety properties; behavior equivalence must be verified rigorously. After this slice, run the full integration test suite multiple times and compare traces against pre-refactor baselines.

**Completion**: All anchor-related tests pass. Framework `eva/anchor/` contains no Linux-specific reason strings, profile names, or rule details.

### Slice A-6: Outcome observers and skill library separation

Move outcome observer logic to per-action observers in `scenarios/linux_runtime/outcome_observers/`. Move current skill library contents to `scenarios/linux_runtime/prior_skills/` (Phase A treats all current skills as Linux scenario priors; the prior/habit/inherited separation is Phase B).

Framework retains:
- OutcomeVector schema (current schema, not multi-dimensional yet — that's Phase B)
- SkillRegistry interface (current single-pool structure, refinement is Phase B)

**Completion**: Outcome and skill tests pass. Linux-specific outcome interpretation logic resides in scenarios/linux_runtime/.

### Slice A-7: Runner introduction and main.py refactor

Create `runners/run_linux.py`. It:
- Imports `eva/` framework
- Imports `scenarios/linux_runtime/` content
- Calls a framework loader function that registers scenario content
- Starts the agent

Refactor `eva/kernel/main.py` so it no longer hardcodes Linux content imports. Existing `main.py` becomes a generic agent loop; Linux startup logic moves to the runner.

**Completion**: `python -m runners.run_linux` (or equivalent) starts the agent and reproduces pre-refactor behavior. Original entry points may continue to work via thin compatibility wrappers, but the canonical entry is the runner.

### Slice A-8: Documentation migration and archival

Migrate `docs/eva-agent-full-implementation.md` content:
- Framework portions → fill into `docs/eva-framework-implementation.md` (replacing skeleton text with actual content)
- Linux scenario portions → fill into `scenarios/linux_runtime/SPEC.md` (replacing skeleton with actual content)
- Original document → moved to `docs/archive/eva-agent-full-implementation-v0.5.md`, header updated to mark as archived

Update `docs/current-status.md` to reflect the new code organization. Update `maintainer/development/module-organization-contract.md` to reflect framework/scenario boundary as canonical.

**Completion**: Documentation reflects the new organization. No reader is misled into thinking framework code includes Linux specifics.

## 5. Per-slice workflow

For each slice:

1. **Open intake**. Update `maintainer/development/current-intake.md` with:
   - Slice identifier (A-1 through A-8)
   - Specific files to be moved or modified
   - Specific tests that must continue to pass
   - Behavior equivalence verification approach for this slice

2. **Boundary check**. Before writing code, verify against this document and the framework/scenario contract:
   - What exactly is being moved?
   - Where is it going?
   - Does the move preserve behavior?
   - Is anything being added that should not be added?

3. **Implementation**. Make the changes. Run targeted tests after each meaningful change.

4. **Full regression**. After implementation, run the full test suite. All tests must pass without logic modification.

5. **Trace verification** (for slices A-2 through A-7). Run the agent on a representative scenario and compare its traces to a pre-refactor baseline. Equivalence is required at this level too.

6. **Update tracking**. Append slice completion record to `maintainer/development/phase-a-refactor-progress.md`. Update `docs/current-status.md` to reflect what has changed.

7. **Architect review** (mandatory at slices A-2, A-5, A-7, A-8). Notify the architect; do not start the next slice until review confirms the current slice is complete and correct.

## 6. Hard constraints

These are not negotiable. Violation means the work is not Phase A and must be rolled back.

**No new behavior.** No new drive types, sensors, actions, anchor rules, outcome dimensions. If a refactor seems to require new behavior to maintain equivalence, stop and report — the refactor approach is wrong, not the constraint.

**No test logic modification to make tests pass.** Import updates are acceptable. Logic changes are not. If a test fails after a move and cannot pass with import updates only, stop and report.

**No schema changes to persistent files.** The audit, memory, learning, habit, and LLM advisory audit file schemas remain identical. Phase A is about code location, not data format.

**No bypass of framework mechanisms by scenario code.** Even though `scenarios/linux_runtime/` will contain code that was previously in `eva/`, it must access framework mechanisms only through the scenario contract interfaces. No direct manipulation of internal framework state from scenario code. (The contract `scenarios-SPEC.md` lists what scenarios can and cannot do.)

**No new release authority.** This is the most important constraint. Even if a refactor seems to require giving release authority to scenario code (to keep tests passing), this is forbidden. Only the framework's mediator issues ReleaseTokens. If maintaining behavior equivalence seems to require a scenario-side release path, the refactor approach is wrong.

**No "while we're at it" improvements.** A refactor slice does not include unrelated cleanup, even if the cleanup looks obviously good. Cleanup is separate work, performed in separate slices, with its own intake.

## 7. Architect review checkpoints

The architect reviews at:

- **After A-2**: Drive registry separation. This sets the pattern for all subsequent separations. If the pattern is wrong, finding out now is much cheaper than finding out at A-7.
- **After A-5**: Anchor rules separation. Anchor is core to EVA's safety properties; the architect must verify framework retains the right mechanisms and scenario retains the right rules.
- **After A-7**: Runner introduction. This is the moment Linux EVA starts running through the new entry path. The architect verifies trace equivalence against pre-refactor baselines.
- **After A-8**: Documentation migration. Phase A complete. The architect signs off on Phase A as a whole.

Between checkpoints, Claude Code proceeds slice by slice without waiting for architect input, but stops if any hard constraint is at risk.

## 8. What to do if Phase A reveals deeper issues

If during Phase A, code reveals that the v0.5 implementation has structural issues that prevent clean separation (for example, framework code that fundamentally cannot operate without knowing specific drive names), do this:

1. Stop the slice in progress.
2. Document the issue in `maintainer/development/phase-a-blockers.md` with:
   - What was discovered
   - Why it prevents clean separation
   - What change would be required
3. Notify the architect.
4. Do not proceed with workarounds, especially workarounds that compromise the framework/scenario boundary.

The architect will decide whether the issue requires:
- A revision to the framework boundary (making certain things scenario-specific that the skeleton documents had assumed were framework)
- A revision to the scenario contract (allowing certain things scenarios can do that were previously prohibited)
- A targeted small-scope behavior change to enable clean separation (if so, this becomes an authorized exception to the "no new behavior" constraint, with explicit scope)
- Acceptance that a particular file's location stays imperfect for Phase A and is addressed in a follow-up

The point is that Phase A's "no new behavior" constraint is strict but not blind. If clean separation genuinely requires a small behavior change, that decision is the architect's, not Claude Code's.
