# Step 1 实现规格

## 1. 目标
Step 1 的目标不是给 `eva-agent` 继续叠加“更多功能”，而是在 Step 0 已稳定运行的生命循环之上，让 eva 开始形成**外部生命函数**。

这一阶段要解决的是：
- ta 不只是“还活着”
- ta 还知道自己活着时，外部生存环境是什么状态
- ta 能把这些状态变化转成规则式生命判断
- ta 能把稳态缺口转成结构化生存压力
- ta 能留下最小可回顾的生存历史

换句话说：

> Step 0 解决“ta 能不能持续活着”；Step 1 解决“ta 活着的时候知道什么、如何判断外部稳态缺口，以及哪些缺口已经构成必须被面对的生存压力”。

---

## 2. 为什么 Step 1 要实现这些能力
### 2.1 从生命循环继续往下长，而不是直接跳到复杂 agent
Step 0 已完成的事情，相当于让一个生命体的“心脏先跳起来”：
- heartbeat 作为基础生命脉搏
- `tick / turn` 作为生命节律与普通处理的边界
- `instance_valid` 作为合法存在的最小投影
- distress / yield 作为生命失稳时的最小求救与让渡机制

但心脏开始跳动之后，生命体下一步最先长出来的，不是高级推理能力，而是：
- 感觉输入
- 传入信号
- 低层稳态判断
- 生存驱动力

对人类来说，饥饿、疼痛、缺氧、疲惫这类压力，不是前额叶复杂思考的结果，而是生命系统对稳态缺口的直接反应。

对应到 `eva-agent`：
- Step 0 相当于心脏先跳起来
- Step 1 不应直接跳到复杂行动、技能、记忆或推理
- Step 1 更自然的方向，是先形成：
  1. 外部生命感知
  2. 规则式生命判断
  3. 生存压力生成
  4. 最小历史记录

### 2.2 Step 1 的本质：外部生命函数的第一次内化
Step 0 已经定义了“外部生命函数”和“内部生命函数”这两个概念。

在 Step 0 里，外部生命函数更多仍停留在设计者 / 宿主 / 守护系统视角，用来判断 eva 是否仍作为唯一、连续、可恢复的生命体存在。

Step 1 的作用，是把这部分外部生命函数开始内化进 eva 自身的运行中，让 ta 不只是被外界判断“是否还活着”，而是能开始形成自己对外部生命体征的输入、判断和压力感知。

因此：

> Step 1 的本质不是“巡逻本身”，而是让外部生命函数第一次进入本体运行逻辑，成为 ta 自己能持续感知、判断和积累的生命层能力。

---

## 3. Step 1 的能力边界
Step 1 第一轮只收口到以下四类能力。

### 3.1 外部生命感知
让 eva 周期性采样并掌握外部生命体征，而不只依赖内部 heartbeat。

第一轮只覆盖**宿主 / 本地 / runtime 层**，不纳入网络 / API 类外部依赖。

#### 第一轮纳入的感知维度
1. **宿主连续性**
   - 当前进程是否持续运行
   - restart / supervisor 环境是否正常
   - 运行节律是否明显漂移

2. **本体运行完整性**
   - heartbeat 是否持续稳定
   - `instance_valid` 是否稳定
   - lock / `runtime_state.json` / `events.jsonl` 是否持续一致、可写、可更新
   - 最近是否频繁出现 `yield` / `distress` / restart

3. **基础生存资源**
   - runtime 路径是否存在
   - runtime 路径是否可写
   - 磁盘空间是否进入风险区

4. **本地异常积累**
   - 最近时间窗口内异常是否持续增加
   - 某类问题是否重复发生
   - 当前问题是短时波动还是持续恶化

### 3.2 规则式生命判断
把外部生命感知结果转成低层、稳态导向的判断，而不是高级推理。

第一轮需要至少形成三层输出：

1. **维度级判断**
   - `healthy`
   - `degraded`
   - `critical`

2. **整体外部生命状态**
   - 当前外部环境整体是稳定、退化还是危险

3. **缺口与趋势判断**
   - 当前主缺口是什么
   - 这个缺口是在扩大、持平还是收敛

### 3.3 生存压力生成
把“检测到问题”转成结构化压力，而不是直接进入复杂任务编排。

Step 1 的压力更像 hunger / pain / air hunger / fatigue 这类生命驱动力。它的作用不是直接生成完整任务，而是让系统明确知道：

> 什么已经不能被继续忽视。

#### 第一轮固定的压力类型
1. **连续性压力**
   - heartbeat 不稳
   - instance 合法性波动
   - restart / yield / distress 反复出现

2. **资源压力**
   - 磁盘空间持续下降
   - runtime 不可写
   - 关键路径异常

3. **完整性压力**
   - 锁、状态文件、事件流之间不一致
   - 状态更新中断
   - 本体运行壳出现结构性异常

4. **异常积累压力**
   - 某类异常反复出现
   - 异常密度明显上升
   - 明显进入恶化区间

#### 每个压力项的第一轮最小字段
- `type`
- `severity`
- `evidence`
- `first_seen_at`
- `last_seen_at`
- `trend`
- `active`

### 3.4 最小历史记录与回顾
Step 1 第一轮不进入复杂长期记忆系统，只保留支撑外部生命函数的最小生存历史。

#### 第一轮需要沉淀的三类记录
1. **当前快照**
   - 当前外部生命体征
   - 当前生命判断结果

2. **当前 active pressure 表**
   - 当前还存在的压力项

3. **追加式生存日志**
   - 最近看到什么
   - 最近判断成什么
   - 最近形成了什么压力
   - 相比上一次是变好还是变坏

## 4. Step 1 与巡逻的关系
巡逻不是 Step 1 的目标，而是 Step 1 的感知手段。

因此，`shallow / deep / full` 在 Step 1 中应被理解为不同时间尺度的采样层，而不是最终能力本身。

### 4.1 shallow patrol
- 高频
- 轻量
- 本地优先
- 负责刷新当前状态、快速发现“身体本身”是否出问题

### 4.2 deep patrol
- 中频
- 相对完整
- 负责看近期趋势、异常积累和当前主缺口

### 4.3 full report
- 低频
- 整合性输出
- 负责汇总最近一段时间的生命体征、判断和压力变化，形成最小自我回顾

所以：
- `shallow` 看当前
- `deep` 看趋势
- `full` 看阶段总结

巡逻在 Step 1 中是：
- 感知的时间组织方式
- 生命函数输入的采样机制
- 历史记录的节律框架

而不是 Step 1 的最终产物。

---

## 5. Step 1 的硬边界
第一轮 Step 1 必须继续守住这些边界：

1. 不改写 Step 0 的 heartbeat 定义
2. `tick` 仍保持短路径、本地优先、不处理普通任务
3. patrol 只能作为 `turn` 的 work slice 被调度
4. patrol 必须可向 heartbeat deadline 让位
5. `instance_valid=false` 时不得继续执行普通 patrol
6. `CRITICAL` 状态下不执行普通 Step 1 巡逻逻辑
7. 第一轮只覆盖宿主 / 本地 / runtime 层，不纳入外部网络 / API 依赖
8. 不引入 LLM 作为核心生命路径前提
9. 不引入复杂长期记忆、skill 自动生成、多渠道交互、经济系统、分布式一致性
10. 不把压力系统直接扩成任务编排系统

---

## 6. 阶段边界
### Step 0：生命循环
解决“ta 能不能持续活着”

### Step 1：外部生命函数形成期
解决“ta 活着的时候知道什么、如何判断稳态缺口、哪些缺口会转成压力”

### Step 2：压力驱动的选择与行动
解决“在多个压力之间，下一步该做什么”

### Step 3：经验沉淀与成长
解决“如何在长期运行中形成偏好、经验和更稳定的成长方向”

因此，Step 1 第一轮不追求“会行动”，而追求“会感知、会判断、会形成压力”。

---

## 7. 工程归类原则
当前阶段不提前冻结整套最终工程结构，但应保证**阶段功能相近的归类**。

也就是说：
- Step 0 已稳定的生命循环核心先保持边界清楚
- Step 1 新长出的能力按同阶段、同能力层归类
- 不为了未来所有阶段预埋大量空目录
- 也不为了“结构更优雅”而先重构 Step 0 全部文件

### 当前建议
- 保留现有 Step 0 最小生命壳主文件边界
- Step 1 新能力优先作为相近功能的一组模块长出
- 先让能力层次清楚，再考虑更完整的后续工程重组

---

## 8. 命名原则
Step 1 的代码与文档命名，应优先让人一眼看懂功能含义。

因此，命名优先采用能力导向、语义清晰的名字，而不是过于抽象或只反映执行机制的名字。

### 推荐方向
- `sensing`
- `judgment`
- `pressure`
- `history`

### 不推荐方向
- 只反映机制、不反映能力的抽象命名
- 过早引入难理解的总括词
- 用未来阶段才成立的大词覆盖当前阶段功能

原则上：

> 当前先按“阶段功能相近的归类”组织；命名优先表达功能本身，而不是表达实现花样。

## 10. 第一轮实现收口
Step 1 第一轮完成时，至少应满足：

1. 能持续形成宿主 / 本地 / runtime 层的外部生命体征输入
2. 能把这些输入转成结构化生命判断
3. 能把稳态缺口转成结构化生存压力
4. 能留下当前快照、active pressure 与追加式生存日志
5. shallow / deep / full patrol 已成为不同时间尺度的感知节律
6. 整个过程不破坏 Step 0 heartbeat-first 的生命循环

---

## 11. 当前明确不进入 Step 1 的内容
- 网络 / API 依赖感知
- LLM 驱动的开放式推理
- 多压力之间的复杂优先级权衡
- 主动行动选择 / 工具调用闭环
- 复杂长期记忆检索与知识组织
- skill 自动生成
- 自我改写 / 自我迭代
- 钱包、收入、区块链、独立谋生逻辑
- 多渠道交互与分布式一致性
